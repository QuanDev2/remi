## End Vision

A personal assistant that ingests Quan's documents, photos, calendar, email, and other personal data, accessible hands-free (e.g. while walking), able to take actions (check email, check tax return, send messages). Eventually runs on a local LLM for privacy and cost.

## Why This Matters (Core Motivation)

Quan does not want to be tied to sitting at a computer typing and reading to build software. The real goal is a voice-first development workflow: walk in the park, talk through what should be built, the agent reports progress and findings at a high level, flags anything visual (screenshot, diff, rendered UI) to the phone screen for a quick glance, then steering resumes by voice. This is not a voice novelty feature, it's meant to replace sit-down coding sessions as the primary way Quan builds.

This also means the app being scoped here serves two purposes at once: it's the tool Quan uses daily to build other things (starting with Folio and this assistant itself), and it doubles as the foundation for the longer-term personal assistant vision, since the voice-plus-visual-glance interaction pattern is the same either way.

Secondary idea (parked, not a priority): this voice-plus-visual-review pattern for AI-assisted development could potentially be productized or monetized later (subscription SaaS, or open-core with a hosted version). Explicitly deprioritized, Quan wants to live with it himself first and find the rough edges before considering monetization.

## Phased Approach

- **Phase 1 (now):** Cloud model (Claude Code) as the brain. Build the surrounding architecture cleanly so phase 2 is a swap, not a rebuild.
- **Phase 2 (later):** Local LLM via Ollama/llama.cpp once Quan buys dedicated hardware. Adds document ingestion, vector search (RAG), persistent memory.

## Current Infrastructure

- Synology DS923+ NAS (quad-core AMD, RAM upgradeable to 32GB) — sufficient to host the phase-1 server.
- Tailscale already configured — this is the secure tunnel to use, no need to expose ports publicly.
- Plan: run Claude Code inside a container (Synology Container Manager) on the NAS, SSH/Mosh in from phone or laptop.

## Voice Layer — Why It's Non-Trivial

SSH/Mosh carries text only, not audio. Apps like ChatGPT/Claude voice mode sidestep this entirely by building mic capture + speaker playback directly into the app, talking to the cloud over a dedicated streaming connection — not through a terminal protocol.

**Decision:** Build a custom phone app rather than bolt audio onto Mosh.

## MVP Architecture (3 layers)

1. **Brain:** Claude Code running in a container on the NAS (unchanged from base setup).
2. **Transport:** Persistent WebSocket connection between phone app and NAS server, carrying text and audio both directions.
3. **Phone app:** One screen — mic button (or paste transcribed text from Whisper Flow, which Quan already uses and is happy with), scrolling conversation text view, speaker output for TTS audio.

NAS-side server: Small backend sitting between the WebSocket and Claude Code. Takes incoming text → feeds Claude Code → gets response → converts to speech (e.g. edge-tts) → streams text + audio back down the socket.

MVP scope explicitly excludes document ingestion, calendar, and email tools — just talk to Claude Code and hear it talk back.

## Tech Stack Decision

**Python, not Node.js** — reconsidered mid-conversation. Rationale:

- Claude Code is writing the code either way, so team familiarity doesn't drive the choice.
- Node was the initial lean (single-language stack with a React Native frontend), but since phase 2's local-LLM ecosystem (Ollama, LangChain-style agent frameworks, vector DBs, local Whisper) is overwhelmingly Python-native, starting in Python avoids a language migration later.
- Python's WebSocket support (FastAPI, websockets) is equally capable — this was not a technical limitation, purely an ecosystem/continuity call.

**Frontend:** React Native (leans on existing React/Folio experience), cross-platform.

## MVP Milestones (Restructured — Agent Team Comes First)

Key reordering decision: the eight-role agent team plus shared ledger is not a feature layered on top of the voice app — it's the operating system Quan wants to use to build everything, including the voice app itself. So it must work first, in plain text with Claude Code, before any voice or mobile layer is built on top of it.

1. **Agent team + shared ledger, working in plain text.** Stand up the eight-role pipeline (goal setter, planner, plan reviewer, human gate, executor, code reviewer, test planner, test executor) and the Postgres shared ledger table, operating through Claude Code as-is (no voice, no phone app yet). Prove the loop actually works and saves time: goal setter writes verifiable acceptance criteria, planner sequences work, plan reviewer surfaces concerns, Quan approves via the gate, executor builds, code reviewer checks, test planner writes scenarios, test executor runs them (unit / integration / end-to-end via Playwright), all logged to the ledger. This is the real milestone one — everything below assumes this works.
2. **Pipe works end to end.** Claude Code (now running as the agent-team pipeline) running in a container on the NAS, reachable from the phone app over a persistent WebSocket. Raw text and voice both flowing in both directions, no filtering or style shaping yet — just proving the connection is solid.
3. **PM-style communication layer.** Prompt engineering, not a new tool. The pipeline is instructed to brief Quan like a PM or engineering manager would be briefed: short status updates, explicit roadblocks, options framed with pros and cons, then stop and ask for direction — never a wall of text. Includes context-window self-awareness: the agent tracks its own token usage and proactively flags when it's approaching the limit, querying the shared ledger to reconstruct ground-truth context in a fresh session rather than relying on a traditional handoff note.
4. **Visual handoff.** The agent recognises when something is inherently visual (a screenshot, a diff, a rendered UI) and pushes it to the phone screen instead of narrating it in speech. Quan glances, taps back into the voice conversation, steering continues.
5. **Hardening.** Session persistence so the app can be closed mid-walk and resumed later without losing state; graceful handling of a dropped or flaky connection.

## Shared Progress Ledger (replaces simple handoff notes)

Rather than relying on a single agent passing an increasingly lossy handoff note to its future self, the design is a durable, queryable log that any agent can read from — the current Claude Code session after a context reset, a separate testing agent, a future code-review agent, etc.

- Every meaningful action (feature completed, decision made, test run, bug found) gets written as a structured entry: timestamp, what changed, why, and status.
- Postgres is the natural choice since Quan is already using it for Folio — gives queryable structure rather than parsing markdown files.
- Solves the context-limit problem directly: instead of needing a traditional handoff note, a fresh session just queries the ledger for recent entries and reconstructs ground-truth context from there, rather than depending on conversation memory.
- Sets up the multi-agent future cleanly: testing agents and review agents can consume the same ledger without needing to be looped into the original conversation at all.

## Multi-Agent Setup (Future Extension)

Longer-term vision includes a multi-agent pipeline: planner, plan reviewer (Quan approves plans), code writer/executor, code reviewer, tester, etc. Open design question was how these agents communicate findings, plans, and decisions with each other.

**Decision:** One unified ledger table (not separate tables per activity type), distinguished by a `type` column. Reasoning: separate tables per activity (findings-only, planning-only, dev-only) force any agent wanting a full timeline to query and stitch together multiple tables. One table with a type field supports both narrow queries (just open findings) and broad ones (full chronological history) from a single source.

**Interaction model:** Agents don't message each other directly — they read and write to the same shared ledger, like a structured meeting log. Example flow: plan reviewer finds an issue, writes a row (type: finding, status: open, referencing the plan/section). Planner queries for open findings tied to its plan, addresses them, writes its own row marking the finding resolved with reasoning.

### Sketch Schema for the Shared Ledger Table

| Field | Purpose |
|---|---|
| `id` | unique entry ID |
| `timestamp` | when the entry was written |
| `agent` | who wrote it (planner / reviewer / coder / tester) |
| `type` | plan / finding / code_change / test_result / decision / approval |
| `status` | open / resolved / approved / rejected |
| `reference` | links to what it's about (feature ID, plan ID) so related entries chain together |
| `content` | human-readable text summary |
| `code_location` | file path and line number (or line range) being referenced, kept as its own structured field rather than buried in free text, so any agent or Quan can jump straight to the exact spot a finding relates to |
| `details` | structured field (JSON) for other specifics, e.g. which file changed, which test failed |
| `resolved_by` | points back to the entry that closed this one out, enabling traceability of a single thread (e.g. bug found → fixed → retested) across multiple agents |

This same table serves both the context-reset use case (single agent re-orienting itself) and the multi-agent coordination use case (different agents reading each other's work) — same structure, no need for separate systems.

## Human-in-the-Loop Gating (Important Refinement)

Full agent-to-agent autonomy is explicitly **not** the default desired behaviour — Quan wants the option of a human approval gate between agent handoffs (e.g. planner finishes → briefs Quan → Quan invokes reviewer → reviewer briefs Quan with findings → Quan directs planner to address specific points).

**Design resolution:**

- Keep the ledger (persistent record) and add a lightweight event bus (e.g. Redis pub-sub, already likely in the stack via Folio) on top for real-time "wake up" notifications between agents — ledger is the record, event bus is the doorbell.
- Layer a policy setting per workflow/stage: autonomous mode (event bus wakes the next agent directly) vs. gated mode (an event that would trigger another agent instead notifies Quan first, who briefs verbally and gives a go-ahead or specific direction).
- Quan's approval/direction itself becomes a ledger entry (type: approval or type: decision), referencing the finding or plan it unlocks. The next agent's trigger waits on/checks for that entry before proceeding.
- Net effect: the ledger captures not just what agents did, but every point Quan steered — a complete audit trail including human decisions, not just agent activity.
- Gating should be toggleable per stage — fully gated by default, with specific stages opened up to autonomous mode only once trusted.

## Agent Team Structure (Critically Reviewed)

Initial proposal was six roles (planner, plan reviewer, human gate, code executor, code reviewer, tester, goal setter). This was pressure-tested and refined through discussion — conclusion: not overkill, provided every role has a genuinely distinct job with no overlap. A "start with 3 roles and expand later" suggestion was explicitly rejected by Quan in favour of building the full accountable loop from the start, given everything is grounded in verifiable acceptance criteria rather than subjective judgement.

### Final Team Structure (8 roles, including Quan as gate)

1. **Goal setter** — Defines the ultimate goal and verifiable acceptance criteria in plain language upfront, before planning starts (e.g. "when a user uploads a photo larger than 10MB, the system should reject it with a specific error"; "a POST request with a missing field should return a 400 response"). This is the actual starting point of the pipeline — planner and reviewer both need this to exist first.
2. **Planner** — Sequences the work needed to satisfy the acceptance criteria.
3. **Plan reviewer** — Scrutinises the plan and surfaces concerns before Quan reviews it. Explicitly kept in from the start (not deferred) — Quan wants to hear the plan reviewer's scrutiny as a first-pass assistant, then do his own review on top, briefed PM-style, rather than parsing the raw plan cold himself.
4. **Human gate (Quan)** — Approves the plan (with the plan reviewer's findings already surfaced), or directs specific changes. Approval is itself a ledger entry (see Human-in-the-Loop Gating section above).
5. **Executor** — Builds/writes the code per the approved plan.
6. **Code reviewer** — Reviews the executor's code output.
7. **Test planner** — Independent from the test executor. Reads the goal, plan, and acceptance criteria, and writes test plans/scenarios in plain language (not test code) — i.e., what should happen under what conditions. Kept deliberately separate from the agent that writes/runs actual test code, because if the same agent both defines what correct behaviour looks like and writes the mechanical tests, it can unconsciously write tests that match what was built rather than what was actually asked for — defeating the purpose of verification.
8. **Test executor** — Takes the test planner's scenarios and turns them into actual runnable tests (unit tests, integration tests, or end-to-end tests via Playwright for real user-flow simulation), executes them, and reports pass/fail back to the shared ledger.

### Verification Granularity (types of acceptance criteria / tests)

- **Unit-level** — Does this function return the correct output for a given input? Fastest and cheapest to catch bugs.
- **Integration-level** — Does this API endpoint actually persist to the database and return the correct shape? (Relevant to Folio's backend specifically.)
- **End-to-end** — Does the full user flow actually work (e.g. upload a photo, see it appear in the library)? Playwright is the right tool here for simulating real browser behaviour.

Every meaningful unit of work should be reviewed AND tested — not just spot-checked.

## Dual-Output Principle (Applies to Every Agent)

Every agent in the pipeline produces two distinct outputs, not one:

1. **Technical detail → the shared ledger.** Full, structured, machine-readable detail: exact test failures, stack traces, screenshot references, file/line locations, assertions, code diffs. This is how agents communicate with each other and how future sessions reconstruct ground truth. Nothing is lost or simplified here.
2. **PM-style brief → spoken to Quan.** A distilled, concise, human-facing summary derived from that same ledger entry — never raw logs or a wall of text. E.g. for the test executor specifically: "three tests failed, here's the pattern, here's a screenshot of the visual regression, here's what I think is going on" — with any visual (screenshot, diff) pushed to the phone screen per the Visual Handoff milestone, while the narration happens by voice.

This dual-output pattern is universal across all eight roles, not specific to any one agent — the ledger entry is always the complete, technical record; the voice brief is always the short, human-readable distillation of it. This is what keeps the ledger useful as ground truth while keeping Quan's actual experience voice-first and free of information overload.
